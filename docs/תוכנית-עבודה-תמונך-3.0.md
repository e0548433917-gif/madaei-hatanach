**התיאור שלך (ד׳ באב):** ״עדיין לחיצה על מעבר לתוסף עוברת, אך לא מופיעה כלל כרטסת הזיהוי.״ שאלת על כך גם בפורום.

הקוד של 2.11.0 עשה בדיוק את מה שמהדורה 1 הציעה — `setPendingIdentify` → `bringToFront` → המופע החדש קורא ומציג. **אבל זה לא עובד.** יש שתי סיבות אפשריות, ושתיהן זולות לבדיקה ולתיקון:

### חשד א׳ — הערך נשמר כאובייקט, לא כמחרוזת (הכי סביר)

```js
// router.js:1775 — מה שיש היום
storageSet(PENDING_IDENTIFY_KEY, { text: text, mode: mode, ts: Date.now() })
```

מהדורה 1 של התוכנית כתבה במפורש `value: JSON.stringify({...})`. **היישום השמיט את ה-`stringify`.** אם `storage.set` של אוצריא מצפה למחרוזת, האובייקט מומר ל-`"[object Object]"`, בקריאה חוזרת ה-`JSON.parse` נכשל, `rec` הופך ל-`null` — ו**שום דבר לא מוצג**. זה מסביר את התסמין בדיוק: המעבר ללשונית קורה (כי `bringToFront` רץ בנפרד), אבל התוצאות לא.

הראיה התומכת: `consumePendingIdentify` כבר מכיל `if (typeof rec === 'string') JSON.parse(rec)` — הכותב חשד בזה בעצמו, אבל תיקן רק את צד הקריאה ולא את צד הכתיבה.

**בדיקה:** לשמור, לקרוא מיד, ולהדפיס את התוצאה ב-`notifications.showInApp`. חמש דקות.

### חשד ב׳ — שני מופעים, והמופע הגלוי לא קורא את המפתח אף פעם

`consumePendingIdentify()` נקרא **רק פעם אחת**, בתוך `waitForOtzaria`, בזמן טעינת המופע. אם אוצריא מריצה מופע רקע (זה שמקבל את `reader.context_menu_item_clicked`) **ומופע לשונית נפרד שכבר טעון**, אז:

* מופע הרקע מזהה, כותב לאחסון, מצייר overlay ב-DOM שאיש לא רואה, וקורא ל-`openSelf`;
* מופע הלשונית עולה לחזית — אבל ה-`waitForOtzaria` שלו רץ לפני דקות, והוא לעולם לא יבדוק שוב.

**התיקון אם זה המצב — לא להסתמך על זמן הטעינה בלבד:**

```js
document.addEventListener('visibilitychange', () => {
  if (!document.hidden) consumePendingIdentify();
});
window.addEventListener('focus', consumePendingIdentify);
```

בתוספת פולינג קל (כל 1.5 שנייה, רק כשהמסמך גלוי) כרשת ביטחון. זה עמיד לשתי הארכיטקטורות גם יחד.

## חלק ד׳ — מנוע הזיהוי v2: האבחון והפתרון

זה לא ״כיוונון״. שני מנגנונים מייצרים כמעט את כל השגיאות:

**א. `candidateForms` מקלף אותיות שימוש בלי לבדוק אם זה חוקי.** `מַחֲנֵה` → מקלפים מ׳ → `חנה` → פגיעה. אבל `מַ` בפתח **אינה** מ׳ השימוש (שהיא `מִ` בחיריק+דגש או `מֵ` בצירי). הניקוד פוסל את זה בוודאות.

**ב. `looseForm` (כתיב חסר) מוחל גם על פעלים.** `וַיִּשְׁאֲלוּ` → `וישאלו` → הסרת ו׳/י׳ → `שאל` → מתאים לצורה הרזה של `שאול` → ״שאול / יהונתן בן שאול״. אותו מנגנון נותן ״ויאמר״→אמר, ״ישראל״→יעקב.

**השורש: `tokenizeHeb` מסירה ניקוד בשורה הראשונה** ומאבדת את המידע המבחין ביותר שיש. הטקסט באוצריא מנוקד וטעום במלואו — משאב שנזרק כרגע לפח.

### שמונה השכבות. כל שכבה מייצרת **ציון**, לא כן/לא

**0. טוקניזציה כפולה.** לכל טוקן שומרים `{raw: 'וַיִּשְׁאֲלוּ', bare: 'וישאלו'}`. כל השאר נשען על זה.

**1. פסילת פעלים** (הרווח הגדול ביותר, זול). ו׳ ההיפוך היא חתימה חד-משמעית: `וַיּ / וַיִּ / וַתּ / וַֽיְ / וָאֶ`. טוקן שמתחיל כך = פועל → לא נכנס לזיהוי (אלא בהתאמה מדויקת מנוקדת לשם). זה לבדו מסלק את רוב הרעש בפסוקי סיפור.

**2. ולידציית אותיות שימוש לפי ניקוד.** מקלפים תחילית **רק** אם היא נושאת ניקוד חוקי לתפקידה:

| אות | ניקוד חוקי כתחילית | דוגמה נגדית |
|---|---|---|
| מ | מִ+דגש, מֵ | `מַחֲנֵה` ❌ (פתח) |
| ב/כ/ל | שווא, פתח, קמץ, חיריק, צירי | |
| ה | פתח/קמץ/סגול + דגש | |
| ו | שווא (וְ), שורוק (וּ) | `וַ`+דגש = פועל ❌ |
| ש | שֶׁ/שַׁ + דגש | |

**3. לקסיקון מנוקד — קציר אוטומטי.** בכל רשומה יש שדה `verses` עם הפסוק המנוקד המלא. נבדק: קציר אוטומטי של הצורה המנוקדת של השם מתוך הפסוקים שלו מצליח על **1,141 מתוך 1,915** אישים (60%) בהתאמה מדויקת בלבד; עם סובלנות לתחיליות ולנטיות סמיכות זה יעלה משמעותית. מה שנשאר — סבב AI חד-פעמי או מקור תנ״ך מנוקד. אחרי זה: `שָׁאוּל` מול `וַיִּשְׁאֲלוּ` — אין התאמה, נקודה.

**4. התאמה ארוכה גוברת, בלי חפיפות.** ״בני ישראל״ תופס את שתי המילים ומונע גם ״בני״ (אישי) וגם ״ישראל״→יעקב.

**5. כתיב חסר — רק כמוצא אחרון.** רק אם אין שום התאמה מדויקת בפסוק, רק לטוקנים שאינם פעלים, ורק באורך 4+ (היום 3).

**6. הקשר הפסוק.** אם התוסף יודע איזה ספר/פרק פתוח — רשומה שיש לה `verse` באותו ספר מקבלת בונוס גדול. (לבדוק אם ה-payload של תפריט ההקשר מוסר `bookId`/`ref`; אם לא — לבקש מאוצריא.)

**7. שלוש דרגות ביטחון בתצוגה:** ✓ ודאי · ~ סביר · ? אפשרי. ברירת מחדל — שתי הראשונות; ״הצג זיהויים נוספים (7)״ פותח את השאר. **זה מה שהופך את הבעיה לפתירה:** לא צריך אלגוריתם מושלם, צריך אלגוריתם שיודע להודות בספק.

**8. סט בדיקות זהב.** 60–100 פסוקים עם התוצאה הנכונה הידועה, נבדקים ב-Node מחוץ לאוצריא. כל זיהוי שווא שתדווח עליו נכנס לסט. בלי זה כל תיקון ישבור משהו אחר ולא נדע.

> ״אני לא רוצה שיגיע למייל שלי, אני רוצה שיגיע לגיטהב, שיגיע לכל העורכים.״

**זה אפשרי, וזו הארכיטקטורה הנכונה — אבל לא ישירות.** הבעיה: כדי לפתוח GitHub Issue צריך טוקן. טוקן בתוך התוסף = כל אחד יכול לחלץ אותו ולכתוב בשמך לריפו. זו הסיבה ש-GitHub Issues ירד מהתוכנית במהדורה 1.

**הפתרון: בדיוק הדפוס של ״דיווח באגים״, רק עם יעד אחר.**

```
התוסף  ──POST──>  שרת ביניים זעיר      ──>  GitHub Issue
                  (Google Apps Script)      הטוקן יושב שם, לא בתוסף
```

* הטוקן נשמר ב-Apps Script — **לעולם לא בקוד התוסף**.
* התוסף שולח JSON פשוט. אותה הרשאת `network.access` שכבר קיימת ב״דיווח באגים״.
* התוצאה: כל דיווח נפתח כ-Issue בריפו הציבורי — **גלוי לכל העורכים, לא במייל שלך**, וניתן לתיוג ולמעקב.
* Apps Script חינמי לגמרי ולא דורש שרת.

**4.1 עודכן בהתאם.** אם בכל זאת יתברר שיש התנגדות לרשת — נשארת נפילה לאחור ל-`feedback.sendEmail`, אבל היעד המועדף הוא גיטהב.

ובנוסף — **שלושה CORS proxy כגיבוי** (`api.allorigins.win`, `corsproxy.io`, `thingproxy.freeboard.io`), למקרה שהבקשה הישירה נחסמת.

**זה מבטל את ״אין ממי להעתיק, תכנון מאפס״ שכתוב במהדורה 1.** משימה 4.2 יורדת מ-45 דקות ל-**25 דקות**: מושכים `manifest.json` מ-`raw.githubusercontent.com/e0548433917-gif/madaei-hatanach/main/manifest.json`, משווים ב-`cmpVersion` (כבר קיים ב-`core.js`!), ואם יש חדש — מציגים הודעה עם קישור ל-Release.

> ״למה בוטל מנגנון העדכון בעיון ההלכה? האם כדי שלא יידרש רשת?״

**כנראה בדיוק מזה.** ולכן הכלל למשימה 4.2: **בדיקת העדכון חייבת להיות שקטה לחלוטין במצב לא-מקוון** — `fetch` בתוך `try/catch` שנכשל בלי אף הודעה, ובלי לעכב את טעינת התוסף. משתמש בלי אינטרנט לא אמור לדעת שהמנגנון קיים.

> ״האם אתה יכול להעלות אוטומטית לחנות של אוצריא?״

**לא יודע, וזה צריך בדיקה — לא אנחש.** לא מצאתי API להגשה לחנות בשום מקום בתוספים שבדקתי. **נרשם כשאלה לפורום אוצריא** (יחד עם שאלת פס הגלילה שכבר שאלת). אם אין — ה-Release בגיטהב הוא ממילא הפצה מלאה, והחנות נשארת עדכון ידני מדי כמה גרסאות.

## ג.7 — התמונות: הסינון ירד, אפשר להשלים ✅ משימת תוכן חדשה

> ״בעבר עבדנו בסביבת נטפרי שחסמה דברים. כעת אני ללא סינון, כך שתוכל להשלים תמונות לכל הכרטיסיות שבעבר נחסמו. למשל בדומם — חצי ללא תמונות.״

**זו הערה חשובה מאוד ולא הייתי יודע אותה.** היא פותחת משימה שלא הייתה קיימת: **ת.4 — השלמת תמונות**. חצי מדומם, וכנראה עוד ערכים בקטגוריות אחרות, חסרי תמונה **רק בגלל חסימת רשת בזמן הבנייה** — לא בגלל שאין מקור.

> ״האם כדאי להוסיף למקומות תמונה אווירית של איך העיר/הנחל/הכפר נראה כיום?״

**כן, וזה רעיון מצוין — אולי הטוב ביותר שהעלית בסבב הזה.** לכרטיס מקום כבר יש קואורדינטות ומפת Leaflet. תצלום אוויר עדכני לצד המפה ההיסטורית הוא בדיוק מה שמקרב את הלומד למציאות — במיוחד לאתרים ארכיאולוגיים שקשה לדמיין, אבל גם לערים מחודשות.

**אזהרה אחת שצריך לשקול לפני שמתחילים:** לתצלומי לוויין יש בעלות. Google Earth ו-Bing אינם חופשיים לשימוש מוטמע. **מה שכן חופשי:** ויקישיתוף (Wikimedia Commons) יש בו הרבה תצלומי אתרים בישראל ברישיון חופשי, ותצלומי ה־USGS/Landsat הם נחלת הכלל. נרשם כ-**ת.5**, עם בדיקת רישוי כשלב ראשון.
